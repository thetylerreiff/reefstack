# Prototype playbook

Use when the user authorizes a disposable experiment to choose a design, interaction, or technical approach. Its deliverable is a supported decision and an explicitly experimental artifact. A read-only question stays in [Investigation](investigation.md); production implementation belongs to [Feature](feature.md). The steps form a [dependency graph](graph.md).

1. **Name the decision.** Identify the uncertainty, constraints, and the observation that could resolve it. **Output:** `question`: a narrow question and success criteria. **Check:** the experiment answers a consequential unknown; facts that can be observed are not turned into unnecessary preference questions.
2. **Bound the experiment.** Choose a small set of meaningful alternatives when comparison helps, and an isolated scratch location without changing production source or shared data. A bounded sketch needs no full delivery ceremony. **Needs:** `question`. **Output:** `bounds`: experiment scope, alternatives, scratch location, and a stopping condition: enough evidence for the decision, plus a stated time or pass limit. **Check:** the user's authorization covers the proposed writes and access.
3. **Build just enough to observe.** Use the lightest implementation that exercises the question, one sketch per alternative; independent sketches can be built in parallel. Keep shortcuts and mocked dependencies explicit. **Needs:** `bounds`. **Output:** `sketch`: a runnable experiment, labeled as disposable. **Check:** the mechanism being decided is real enough to test; a mock cannot establish unimplemented behavior or real-world performance.
4. **Try the alternatives on the relevant surface.** Drive interactions, run commands, or capture observations against the same criteria for every alternative. **Needs:** `question`, `sketch`. **Output:** `observation`: screenshots, measured behavior, or other decision evidence. **Check:** the observation supports a choice, or shows no meaningful difference, which is itself a result; name inaccessible paths and uncertainty instead of treating a sketch as production validation. **On fail:** → step 2 if an alternative cannot be exercised within the bounds. **Repeat:** → step 3 to refine a sketch while a criterion needs finer resolution to decide. **Bound:** the time or pass limit in `bounds`.
5. **Recommend and hand off.** Explain the choice, tradeoffs, unresolved questions, and artifact location. **Needs:** `observation`. **Output:** `decision`: a decision with the experimental limitations. **Completion check:** transition to Feature only when production work is authorized, carrying the `decision`; sketch code is not production code unless reworked under Feature; a prototype request alone does not authorize promotion, installation, deployment, or publishing. Clean up only task-owned resources when appropriate, preserving useful artifacts.
