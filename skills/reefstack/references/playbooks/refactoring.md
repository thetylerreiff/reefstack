# Refactoring playbook

Use for an authorized structural change that should preserve observable behavior. A known, trivial rename can stay direct. New behavior belongs to [Feature](feature.md); a discovered defect belongs to [Bug fix](bug-fix.md). Keep either separate from the refactor unless the user includes it in scope. The steps form a [dependency graph](graph.md).

1. **Pin the contract.** Inspect callers and observable outputs, errors, side effects, and compatibility requirements. When the refactor may be consequential and what relies on the code is not already known, find it with [Blast radius](../../../blast-radius/SKILL.md). **Output:** `baseline`: the behavior to preserve and current baseline evidence. **Check:** a characterization test, representative replay, or equivalent comparison would detect a meaningful behavior change; compiling alone is insufficient.
2. **Choose the smallest useful structure.** Identify the coupling, duplication, or confusing ownership being removed. Use [Design](../../../design/SKILL.md) for uncertain boundaries. **Needs:** `baseline`. **Output:** `structure`: target structure, affected callers, and bounded units of work. **Check:** explain the concrete maintenance benefit; do not add speculative abstraction or silently change public contracts.
3. **Move one verifiable unit.** Preserve concurrent work, migrate affected callers, and remove obsolete paths when compatibility permits. Use existing codemods for mechanical sweeps when appropriate. **Needs:** `baseline`, `structure`. **Output:** `change`: integrated structural changes so far. **Check:** the behavior baseline still passes after the unit; inspect string-based references, configuration, and documentation as well as typed callers. **On fail:** → step 2 if the unit cannot preserve the baseline within the chosen structure. **Repeat:** → step 3 for the next unit while units remain. **Bound:** the units named in `structure`; a new unit needs the user's approval or existing authorized scope.
4. **Prove equivalence.** Compare old and new behavior on representative inputs, including failures and boundary cases. Reuse valid evidence and run affected integration checks. Use [Verify](../../../verify/SKILL.md) for affected checks and verification-map maintenance. A changed public entry point is a behavior change requiring explicit scope, even when internal callers migrate cleanly. **Needs:** `baseline`, `change`. **Output:** `evidence`: revision-specific equivalence evidence and explicit gaps. **Check:** any unexpected difference is resolved or separately authorized; unrelated improvements do not hide inside the refactor. **On fail:** → step 3 for the unit whose behavior differs. → step 1 if the baseline missed a behavior callers rely on.
5. **Review and hand off.** Obtain fresh independent review scaled to the change. **Needs:** `change`, `evidence`. **Output:** `findings`: each accepted or rejected with a reason, with the structural benefit, preserved contract, checks, and remaining limits. **On fail:** → step 3 for an accepted finding in a unit. → step 2 for one about the structure. → step 1 for a missed contract. Then recheck only the evidence it makes stale. **Completion check:** do not commit or open a PR merely because the local refactor is complete.
