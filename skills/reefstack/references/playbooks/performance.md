# Performance playbook

Use for an authorized improvement to measured latency, throughput, resource usage, or another performance target. A request to explain slowness without changes stays in [Investigation](investigation.md). Agree a target or bounded stopping condition before implementation. Stop when it is met, the scoped hypothesis fails, or evidence is unavailable. This is not an open-ended hillclimbing loop: its only loop is the bounded Repeat in step 4. The steps form a [dependency graph](graph.md).

1. **Define and measure the baseline.** Name the user-visible workload, metric, units, target, environment, and source revision. Use representative data and repeat measurements enough to expose noise; account for warmup, caches, and relevant load. **Output:** `baseline`: reproducible commands, baseline artifacts, and the target. **Check:** the measurement covers the actual slow path, not an easier proxy. If access or workload validity prevents measurement, report the limitation rather than inventing a number.
2. **Locate the limiting work.** Use traces, profiles, or focused experiments to distinguish plausible causes. Follow [Diagnose](../../../diagnose/SKILL.md) where useful. **Needs:** `baseline`. **Output:** `hypothesis`: a supported bottleneck and falsifiable improvement idea. **Check:** observations explain the cost; do not infer a performance ceiling from source inspection alone.
3. **Bound and implement the change.** Preserve correctness and explicit resource tradeoffs. Keep the baseline and target in view. **Needs:** `hypothesis`. **Output:** `change`: the smallest justified change and relevant correctness checks. **Check:** one meaningful hypothesis can be evaluated without unrelated optimizations obscuring attribution.
4. **Compare under matched conditions.** Rerun the same workload with comparable hardware, configuration, data, and measurement method; alternate or repeat baseline/candidate runs when drift matters. Compare each pass against the last kept state and the overall target against the original baseline. Keep the task's own change only when the improvement exceeds noise without unacceptable regressions; revert it when the hypothesis is falsified. For an inconclusive result, report it and keep or revert according to the authorized target. **Needs:** `baseline`, `change`. **Output:** `evidence`: before/after values, variation, commands, artifacts, the tested revision, and the result labeled improved, falsified, or inconclusive, kept beside earlier passes. **Check:** correctness still holds, conditions matched, and the label follows from the measurements. **On fail:** → step 3 if correctness breaks. → step 1 if conditions changed and the baseline no longer matches. **Repeat:** → step 2 with a new hypothesis while the target is unmet. **Bound:** the user's decision for each new hypothesis, or one already in the authorized scope; without it, stop and report.
5. **Review and stop at the target.** Obtain fresh review scaled to the change. **Needs:** `change`, `evidence`. **Output:** `findings`: each accepted or rejected with a reason, with measured impact, resource tradeoffs, and remaining limits. **On fail:** → step 3 for an accepted finding in the change. → step 4 if the comparison was not matched. → step 1 if the measurement is a proxy rather than the slow path. Then recheck the measurements it makes stale. **Completion check:** no unsupported speedup claim or indefinite optimization loop.
