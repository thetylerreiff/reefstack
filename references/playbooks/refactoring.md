# Refactoring playbook

Use for an authorized structural change that should preserve observable behavior. A known, trivial rename can stay direct. New behavior belongs to [Feature](feature.md); a discovered defect belongs to [Bug fix](bug-fix.md). Keep either separate from the refactor unless the user includes it in scope.

1. **Pin the contract.** Inspect callers and observable outputs, errors, side effects, and compatibility requirements. For substantial implementation, open or reuse the [task record](../task-record.md) before editing. **Output:** the behavior to preserve and current baseline evidence. **Check:** a characterization test, representative replay, or equivalent comparison would detect a meaningful behavior change; compiling alone is insufficient.
2. **Choose the smallest useful structure.** Identify the coupling, duplication, or confusing ownership being removed. Use [Design](../../skills/design/SKILL.md) for uncertain boundaries. **Output:** target structure, affected callers, and bounded work ownership. **Check:** explain the concrete maintenance benefit; do not add speculative abstraction or silently change public contracts.
3. **Move in verifiable units.** Preserve concurrent work, migrate affected callers, and remove obsolete paths when compatibility permits. Use existing codemods for mechanical sweeps when appropriate. **Output:** integrated structural changes. **Check:** the behavior baseline still passes after each meaningful unit; inspect string-based references, configuration, and documentation as well as typed callers.
4. **Prove equivalence.** Compare old and new behavior on representative inputs, including failures and boundary cases. Reuse valid evidence and run affected integration checks. Use [Verify](../../skills/verify/SKILL.md) for affected checks and verification-map maintenance. A changed public entry point is a behavior change requiring explicit scope, even when internal callers migrate cleanly. **Output:** revision-specific equivalence evidence and explicit gaps. **Check:** any unexpected difference is resolved or separately authorized; unrelated improvements do not hide inside the refactor.
5. **Review and hand off.** Obtain fresh independent review for substantial or consequential changes and recheck accepted fixes. **Output:** the structural benefit, preserved contract, checks, and remaining limits. **Completion check:** reconcile any task record, run its final readback, and copy the exact Record line using [the handoff procedure](../task-record.md#close-the-record-then-hand-it-off). Do not commit or open a PR merely because the local refactor is complete.
